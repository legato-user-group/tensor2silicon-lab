“그래프”란 무엇인가

연산들의 의존 관계를 표현하는 방향 비순환 그래프(DAG)
  • 노드 = 연산, 간선 = 데이터 흐름
  • eager 실행은 파이썬이 한 줄씩 커널을 호출한다 — 다음 줄에 무엇이 올지 모른다
  • 그래프로 잡아 두면 전체를 보고 결정할 수 있다: 무엇을 합칠지, 어떤 순서로 돌릴지, 메모리를 언제 놓을지
  • 이 단계에서 컴파일러는 그래프로 표현된 연산과 의존 관계를 분석한다
x ──▶ floor ──▶ y ──▶ add(1) ──▶ z

# 노드: floor, add
# 간선: x→floor, floor→add(y), add→z

“FX 그래프”란 무엇인가

PyTorch의 자체 그래프 자료구조 — 평범한 파이썬 객체
  • torch.fx.Graph — 노드 리스트를 가진 평범한 파이썬 객체
  • 순회·수정이 쉽다: 노드를 돌면서 바꾸고, 다시 파이썬 코드로 찍어낼 수 있다
  • Dynamo·AOTAutograd·Inductor의 경계에서 FX 그래프를 주고받는다. Inductor 내부에서는 루프 수준 IR도 사용한다
  • 출력이 코드처럼 읽히는 이유: FX 는 그래프를 forward() 함수 형태로 되찍어 준다
# FX 그래프를 코드로 되찍은 형태 (graph_code 로그의 모양)
def forward(self, L_x_ : torch.Tensor):
    l_x_ = L_x_
    floor = torch.floor(l_x_);  l_x_ = None
    add = floor + 1;  floor = None
    return (add,)

    파이썬 코드를 그래프로 변환
    계산은 하지 않고, 데이터 흐름만 추적한다

    • 그래프로 못 넣는 파이썬 동작은 잔여 바이트코드로 남겨 인터프리터가 그대로 실행

    graph break
    그래프가 쪼개지는 지점 — 최적화가 멈추는 지점
    • 원인 ① 텐서 값에 의존하는 제어흐름 — if x.sum() > 0 은 값을 알아야 분기하는데, Dynamo 는 계산을 안 한다
    • 원인 ② 그래프화 불가능한 파이썬 동작 — print, I/O, 외부 라이브러리 호출
    • 결과 함수가 여러 그래프로 쪼개지고, 컴파일된 코드 ↔ 파이썬 인터프리터 사이 문맥 전환이 생긴다
    • 부작용 그래프 경계를 넘는 최적화 기회 소실 — 경계 양쪽 연산은 절대 합쳐지지 않는다
    def a_dynamo_break(x):
    y = x * 2
    if y.sum() > 0:      # ← 여기서 graph break
        return y + 1     #   그래프 1: x*2, sum   /  그래프 2: y+1 또는 y-1
    return y - 1

torch._dynamo.explain(a_dynamo_break)(x)
# Graph Count / Graph Break Count / Break Reasons 를 알려 준다
    CPU 실측: Graph Count = 2, Graph Break Count = 1. 입력은 torch.ones(4). 실제 사유·그래프는 부록 A에 수록.

    class <lambda>(torch.nn.Module):
    def forward(self, arg0_1: "f32[4]"):
        add: "f32[4]" = torch.ops.aten.add.Tensor(arg0_1, 1);  arg0_1 = None

        exp: "f32[4]" = torch.ops.aten.exp.default(neg);  neg = None

    FLOPs와 bytes — 서로 다른 두 가지 비용
    FLOPs는 계산 횟수, bytes는 옮기는 데이터의 크기다
    • FLOPs: 부동소수점 연산 횟수. FLOP/s는 초당 연산 처리량이다.
    • 길이 P 내적은 곱 P번 + 덧셈 P−1번. 관례적으로 약 2P FLOPs로 센다.
    • 행렬곱 [N,P] × [P,M]은 출력 NM개마다 길이 P 내적 → 약 2NPM FLOPs.
    • bytes: 원소 수 × 원소당 바이트 수. FP32는 원소당 4 bytes.
    A: [N, P]    B: [P, M]    C: [N, M]

계산량 ≈ 2 × N × P × M FLOPs

이상적인 최소 데이터 이동량
≈ (NP + PM + NM) × s bytes
s = 원소당 바이트 수

연산 집약도 = FLOPs / bytes

단순 Roofline 관점:
시간 ≳ max(계산 시간, 이동 시간)
    • 단순 원소 연산: 큰 배열에서는 메모리 대역폭이 중요해지기 쉽다.
    • 작은 연산: Python·커널 호출 오버헤드가 더 중요할 수 있다.
    • 행렬곱: shape·dtype·재사용·커널 구현에 따라 병목이 달라진다.
    • Fusion은 메모리 접근과 호출을 줄일 수 있다. 최종 효과는 측정해야 한다.

    심화 — Transformer FLOPs의 가정
    본문의 병목 판단과, 모델 구성요소의 FLOPs 비중을 구분하자
    • 선형층 A[N,P] × W[P,M]: forward ≈ 2NPM. 입력·가중치 기울기까지 계산하면 합계 ≈ 6NPM.
    • Dense Transformer에서 attention 행렬곱 비용 등을 제외하는 근사: 학습 FLOPs ≈ 6 × 파라미터 수 × 토큰 수.
    • Scaling Book의 T / (8D)는 F=4D, MHA, 해당 gated MLP와 학습 계산 가정하에서 dot-product attention / 나머지 주요 행렬곱의 FLOPs 비율이다.
    • T > 8D는 이 비율이 1을 넘는 조건이다. compute-bound의 판정 기준이 아니다.
    • GQA·MLP 구조·causal 계산량 산정·local attention 등 가정이 바뀌면 계수와 임계값도 바뀐다.
